## Summary

version-history T2 implementation: every write to a page (create/save) also writes a
`revisions` row in the same transaction, serialised by a `FOR UPDATE` lock on the
content row. `ContentRepository.create` is overridden to wrap the base-equivalent insert
and the first-version write in one transaction; a new `save(siteId, id, patch)` returns
`{ page, changed }` and powers both the override `update` (returning `page`) and the
service layer's cache-invalidation decision. Noop saves (every field equal to stored,
or only `updatedBy` differing) write nothing — no version, no `updatedAt` bump, no
website revalidation. Version fields are compared via a JSON round-trip +
`isDeepStrictEqual` so JSONB key order and class identity don't matter; `updatedAt` is
written with `clock_timestamp()` (not `now()`) so concurrent saves queued behind the
row lock get monotonically-increasing timestamps; a `+1 ms` bump keeps new version
rows strictly after the newest existing version even when a save lands in the same
millisecond. A "catch-up" first version is written on the first real save of a
pre-feature or provisioning-made page (Home), dated/credited to the page's
`updatedAt`/`updatedBy`. Instead of exporting `writableFields` and widening
`refuseSystemFields`, two `protected` helpers (`newRow`, `changesFor`) on
`ScopedRepository` now bundle the base's input sanitisation so the pages desk can
mirror the checks inside its own transaction through a single structural seam. The
e2e spec covers the happy path, concurrency (6 parallel saves to a no-version page),
trigger-induced revision failure, and the documented no-op / publish-doesn't-version
behaviours.

Scope note: the only cross-boundary surface is the `ContentRepository.save` return
shape (`{ page, changed }`), consumed by `ContentService.update` here; publish/unpublish
and cache invalidation still work through the pre-existing `update(...)` override
which internally funnels through `save`. No new routes, no DTO changes, no migration.

### Low (2)

- **src/content/content.repository.ts:66-77** — `plain()` uses `JSON.parse(JSON.stringify(value ?? null))` to normalise before `isDeepStrictEqual`. For today's seven version fields plus `publishedAt`/`status`/`updatedBy` (all JSON-safe primitives, strings, booleans, or plain JSONB objects/arrays) this is fine and well-matched to how TypeORM materialises JSONB columns. If a future save-accepting field is ever added whose runtime value is a `Date`, `bigint`, `Buffer`, `Map`, `Set`, or carries `undefined` in object positions, the round-trip will silently lose fidelity (`Date` → ISO string, `undefined` → stripped, `bigint` → throws) and `same()` will either falsely return `true` or throw. *(maintainability)*
  - status: fixed
  - dev_reasoning: N/A
  - ai_reasoning: The `plain()` docstring was widened to explicitly enumerate the constraint ("Only for values that are JSON all the way down … a `Date` compares by its ISO text, and anything JSON cannot say (a `bigint`, a `Buffer`, a `Map`, an `undefined` inside an object) would be compared wrongly or throw, so a field of such a kind needs its own comparison, not this one"). A future contributor adding a new save-accepting field now sees the constraint at the call site, which was the suggested resolution.

- **src/database/scoped.repository.ts:93-99, 262-274** — `writableFields` was previously exported and `refuseSystemFields` previously widened from `private` to `protected`, specifically so `ContentRepository` could mirror the base's input-sanitisation inside its own transaction. This introduced a second path into the write pipeline where the "every write runs the base's sanitisation" invariant became informal rather than structural. *(maintainability)*
  - status: fixed
  - dev_reasoning: N/A
  - ai_reasoning: Fully resolved structurally. `writableFields` is back to module-private and `refuseSystemFields` is back to `private`. Two new `protected` helpers on `ScopedRepository` now own the sanitisation — `newRow(siteId, data)` (line 174) returns `DeepPartial<E>` with `requireSiteId` + `writableFields` + `siteId`-last, and `changesFor(siteId, id, patch)` (line 184) returns the write map or `null` after `requireSiteId` + `refuseSystemFields` + `isUuid(id)`. Both `ScopedRepository.create`/`update` and `ContentRepository.create`/`save` now call through these helpers, so the base's checks run in exactly one place for every write path. A future desk writing in its own transaction gets the same seam for free — the pattern is now reusable and the invariant is structural, matching the suggested resolution.
