## Summary

Stack: NestJS 12 + TypeORM.

Extends the demo CLI to produce **two companies with two websites each** (organizations T4). Three
concern changes:

1. **CLI (`src/cli/run-demo.ts`)** — `makeClient` now branches: if the admin account already owns an
   organization with this file's `organization` name, the new file is added as a site to that
   existing org via `provisioning.provisionSite` (the first-by-id when earlier runs left several).
   Otherwise `provisionTenant` makes the organization (and the account, if new) as before. A new
   `removeLeftovers` helper runs after a successful `--replace` to delete the account's empty
   organizations named like a demo company that older demo-code versions left behind. The final
   "Done." line now reports both organization and website counts.
2. **Site-removal desk (`src/site-removal/`)** — adds `removeEmptyOrganization` on the service and
   `deleteEmptyOrganization` on the unscoped repository. Mirrors the existing site-deletion shape:
   service UUID-guards, repository runs one transaction, locks the organization row FOR UPDATE,
   checks `sites.organization_id` is empty, deletes. Returns `{ deleted | has-websites | not-found }`
   via a new `OrganizationRemoval` type; service flattens all non-`deleted` outcomes to `false`.
3. **Demo content + docs** — adds `demo/kettle-and-crumb-wholesale/` and `demo/studio-halden-journal/`
   (each with `content.json` + four reused sibling images). CLAUDE.md, demo/README.md and
   deploy/README.md updated with the shared-organization behaviour and a one-time `--replace`
   migration note for servers that ran the older demo code. E2E coverage: UC-OR-07 (two companies ×
   two websites, people spread across siblings) and UC-OR-08 (leftovers removed on `--replace`, other
   people's same-named orgs left alone, every person met-again, passwords unchanged, run idempotent).

Reviewed against the NestJS criteria in `resources/nestjs.md`:
- The new repository method lives in the correct unscoped desk (`SiteRemovalRepository`, the third such desk)
  and follows the existing single-transaction / pessimistic-write / cascade-via-FK pattern. The FK from
  `sites.organization_id` means a concurrent `provisionSite` insert blocks on the FOR KEY SHARE lock while
  the FOR UPDATE lock is held, so either the delete wins and the insert fails on the FK, or the insert
  commits first and `existsBy(Site)` returns `has-websites` — matches the doc comment.
- UUID validated in the service layer (`isUuid`) before the repository call; no raw string reaches the query.
- `findOrganizationsOwnedBy` returns orgs ordered `(name ASC, id ASC)`; the `.find()` in `makeClient` and
  the `.filter().slice(1)` in `removeLeftovers` therefore agree on which org is kept.
- `removeLeftovers` only runs on `exitCode === 0 && args.replace`, and only touches `.slice(1)` — the
  first-by-id org (which holds the newly made websites) is never attempted.
- Tests are parameterized SQL (`$1`, `$2`) and reuse existing support helpers (`seedUser`, `TEST_PASSWORD`).
- No controller/DTO/auth surface changed (this is a CLI path), so routing/validation/response-shape rules
  are not applicable.
