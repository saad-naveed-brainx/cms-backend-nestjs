## Summary

Platform-admin T2 (D-062): adds `GET /platform/organizations` and `POST /platform/organizations` behind
`PlatformAdminGuard`, backed by two new methods on the unscoped `PlatformAdminRepository`
(`listOrganizations`, `createOrganization`). The create path either makes an existing account the owner
at once, or creates the organisation with no owner plus an `organization_invitations` row (only the
token's SHA-256 is stored; the plaintext is returned once). Also exports `newToken` from
`invitations.service.ts` so it can be reused here, extends the pinned method list in the repo spec, and
adds a comprehensive e2e spec (`test/platform-admin-organizations.e2e-spec.ts`) plus a
`newSuperAdmin` support helper. The tenant-isolation sweep skips `/platform/...` with an explicit
comment pointing to T6.

Stack: NestJS 12 + TypeORM + Postgres. Zod for validation (class-validator is deliberately not
installed per CLAUDE.md). Review covered the controller, service, repository, the raw-SQL list query,
the schema, the guard chain (JwtAuthGuard → PlatformAdminGuard), the `OrganizationInvitation` entity
(unique on `organizationId`, so the `LEFT JOIN` cannot multiply rows), and the test coverage.

The implementation is tight, consistent with the project's existing unscoped-desk conventions
(D-015), the input schema matches `organizationInputSchema` from `POST /organizations` by composition
(not duplication), secrets are handled correctly (token generated only when needed, never persisted),
and the isolation-table skip is correctly placed to exclude platform routes from both the "missing"
and "gone" sides of the comparison. No critical, high, or medium findings.

Note: `git diff --cached` currently fails locally with "fatal: unable to read 4b245ea3..." / missing
blobs (`git fsck` reports 4 missing blobs on this worktree's index). Content was reviewed from the
staged files on disk and from a captured diff; the diff_hash above is computed over that captured

  generated only after the existence check, so it is never generated when an existing account is
  used. Narrow TOCTOU between `findUserByEmail` and the transaction (an account could be created
  elsewhere in that window) is a theoretical concern only; the invitation-accept flow for owners
  arrives in a later ticket and will handle both cases at accept time.
