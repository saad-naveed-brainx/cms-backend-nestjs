## Summary

Adds `GET /organizations/:id/team` (organizations T3): the owner of an organisation
reads its company team — websites, people (merged across sites, with their access
on each), and waiting invitations. Nothing is stored for it: the new
`OrganizationTeamService` composes already-tenant-scoped reads from
`MembersService.list(siteId)` with the owner's own memberships, discovered through
the unscoped `PlatformRepository`.

Scope and quality:
- `OrganizationsModule` now imports `PlatformModule` and `MembersModule` and
  registers `OrganizationTeamService`; `MembersModule` additionally exports
  `MembersService` so the organisation module can call it. No new unscoped desk is
  introduced — tenant isolation (invariant 1 and D-015) is preserved because every
  cross-site read lands on `MembersService.list(siteId)` with a `siteId` the
  service already proved belongs to the caller's org.
- Authorisation is enforced before any site data is fetched: owner → 200, member
  of a site in the org but not owner → 403, everyone else → one 404 with one
  message (owner of another org, stranger, unknown id, malformed id, upper-case
  id). The ownership check runs before any member/invitation query.
- No secrets leave the service: `MemberView` carries only `{ userId, name, email,
  role: { id, name }, isOwner }`, and `InvitationView` is reshaped to drop
  `invitedBy`/`createdAt`; the view type intentionally never carries the token or
  its hash. Explicitly asserted by the e2e test (`not.toContain('password')`,
  `not.toContain(nina.token)`, `not.toMatch(/token/i)`).
- E2E coverage is strong: happy path with two sites and three people (owner,
  Editor on one site, Viewer on both), one waiting invitation; idempotency (no
  row count delta on repeated reads); expired invitation surfaced as `expired:
  true`; 401 for no / expired token; 403 for a non-owner member; same 404
  message for every negative case; case-insensitive id. Nothing is mocked —
  real provisioning, real routes, real sign-ins.
- CLAUDE.md updated to describe the new route and its exact answer shape; wording
  matches the implementation (owner-only, 403/404 split, response fields).

Cross-boundary note (no frontend diff staged): the admin that consumes this
endpoint lives in the `cms-admin` repo and is reviewed on its own branch; this
review covers only the API contract.
