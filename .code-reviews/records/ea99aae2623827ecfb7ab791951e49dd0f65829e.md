## Summary

Stack: NestJS (TypeORM, Zod validation, Vitest E2E). API-only change — no cross-repo contract shifts.

Scope: extends the `npm run demo` CLI (users-roles T8 work being brought onto the T4 branch) so each demo client's `content.json` can list **people** (Editor, Author, Contributor, Viewer) and **credit pages to an author**. Changes:

- `src/cli/run-demo.ts` — adds a reusable `email` Zod schema (trim + lower + `.email().max(254)`), `CREDITED_ROLES` (`Editor`, `Author`), `isHome(type, slug)`, a `checkCredits` `superRefine` that refuses, before any write: a duplicate `people` email, an `author` not in `people`, an `author` whose role cannot publish, or any `author` on the Home page. New `addPerson()` adds each person through the real `InvitationsService.create` + either `InvitationsService.accept` (new account → generated 24-char base64url password printed once) or `InvitationAcceptanceRepository.accept({ kind: 'existing' })` (existing account → password unchanged, matching the users-roles D10 flow). Credited pages are created and published as the person via `SiteMemberRepository.findAccess`, so writes are gated by that person's real role permissions — the same `SiteAccess` a route guard would build. The `--email` owner is refused as a `people` entry up-front (after file parse, before `openApp()`). A failed run now prints a reminder that any generated passwords in the output are the only copy.
- `test/demo.e2e-spec.ts` — switches from injecting a `DemoApp` factory to spying `NestFactory.createApplicationContext`, so `runDemo` exercises its real `openNestApp` path (removing a parallel service list that could drift from `openNestApp`). Adds `[UC-UR-27]` covering: four roles present on each site, each page's `author`/`updatedBy` matches the credited member, each new password appears **exactly once** in the output and verifies against the stored hash via `PasswordService`, `--replace` reuses the same `users` rows and prints `existing account, password unchanged` per person; a second `[UC-UR-27]` variant proves both refusal paths leave `sites`, `users`, and `invitations` unchanged even with `--replace`.
- `demo/{kettle-and-crumb,studio-halden}/content.json` — adds four `people` and `author` fields on Editor/Author-eligible pages; roles on Home are correctly absent.
- `CLAUDE.md`, `demo/README.md`, `deploy/README.md` — doc updates mirroring the behaviour; `deploy/README.md` warns operators that first-run output contains eight single-shown passwords.
- `.code-reviews/ledger.jsonl` and two `records/*.md` — carried over from the T8 branch where this work was originally reviewed and committed; these are review metadata, not production code.

The implementation follows established repo invariants: Zod validates everything up front, non-null assertions (`.find(...)!`, `(await findAccess(...))!`) correspond to documented structural invariants (every site has the five `ROLE_DEFINITIONS`; a just-accepted invitee has a membership) rather than defensive coding; writes go through the same services the HTTP routes use; passwords use `crypto.randomBytes(18)` → 144 bits of entropy, well above the 12-char minimum; and the owner-vs-people clash check runs **after** parse and **before** `openApp()`, so a refusal cannot produce a partial write.
