Scope (organizations T5, `docs/features/organizations/`, D-052, D-054):

- `test/organization-isolation.e2e-spec.ts` (new, 518 lines): three cases the broad tenant-isolation sweep cannot prove:
  - **UC-OR-11** — one person on two organizations is on each team with that organization's website and role only, and neither owner learns of the other organization. Also checks `/auth/me` lists both organizations for Pat, and that a member who is not the owner reading `/organizations/:id/team` is a 403 with no leak.
  - **UC-OR-10** — one owner cannot read, change, or learn of another's organization through the organizations routes. Four spellings of the victim's id (as-is, upper-case, extra letter, the website id reused as an organization id) are all answered the same as a random UUID (404 "Organization not found"), with no leak. Smuggled fields in the body (`ownerId`, `organizationId`, `siteId`/`site_id`) are a 400 (strict schema); smuggled fields in the query string are ignored, the organization is made owned by the attacker, and the owner's `organizationsOwned` counter advances by exactly one. `POST /sites` with the other organization's id is refused with the same shape as a random UUID. Finally, the victim's organization row, its sites row, its owner's organization list, its team, and the website's full `fingerprint()` are byte-for-byte unchanged.
  - **UC-OR-09** — a person on one website of an organization cannot reach, change, or learn of the sibling website in the same organization, whatever their role. Builds a second website (`Pinecone Shop`) under Acorn's organization through the real `POST /sites` route (with its new `organizationId` field), gives it a published page, a draft, a picture, a member, and a waiting invitation. Then an Editor and an Administrator on Acorn's first website only are each run through: (1) the sibling site's id as `X-Site-Id` on six site-scoped doors → 403, same look as a random uuid; (2) the sibling's page/member/role/invitation ids under one's own header on nine routes → ≥400, same look as nowhere-ids; (3) lists `/content`, `/content-types`, `/media`, `/members` under one's own header show nothing of the sibling; (4) smuggled `siteId`/`site_id` in body/address/form on `POST /content` and `POST /media` land in the attacker's own site; (5) `/auth/me` memberships list only Acorn's website and `organizations` lists only Acorn with `ownsOrganization: false`. Closes with `fingerprint(shop.siteId) === fingerprintBefore`.

Correctness, security and consistency checks:

- **Every one of the three new UCs reads the real app, routes, tokens, and database with nothing mocked.** `organization-isolation.e2e-spec.ts` builds its world through `buildWorld()` (same two-clients harness) and reaches into Postgres with parameterised `dataSource.query` calls — no string interpolation of user input into SQL.
- **The `smuggleWrites` owner-column branch is correct.** Reading `src/organizations/organizations.controller.ts`, `POST /organizations` uses `@Body()` only, and `organizationInputSchema` is `z.strictObject({ name })` — so a smuggled `ownerId`/`siteId`/`organizationId` in the body produces 400 (`ProvisionInputError` → `BadRequestException`), while query params are ignored. The address-smuggle test exercises that: 201, owner is the attacker. The new `'owner_id'` branch in `smuggleWrites` compares against `attacker.owner.userId` on the `organizations` row, which matches `createOrganization(userId, ...)` in `provisioning.repository.ts`.
- **The same-look invariant holds for `GET /organizations/:id/team`.** `OrganizationTeamService.team()` lowercases the id, looks it up in the caller's owned list (misses for the victim's or an invented id), falls through to a membership check (misses for every attacker in UC-OR-10 because the attacker is not a member of the victim), and throws `NotFoundException(ORGANIZATION_NOT_FOUND_MESSAGE)`. UC-OR-10's four spellings all land in this same path, and `look()` compares status + message, so all four truly match the absent probe. The 403 (`TEAM_OWNER_ONLY_MESSAGE`) is only reachable by a non-owner member, which UC-OR-11 exercises.
- **UC-OR-10's "same look" check covers the capitals case too.** `rawOrganizationId.toLowerCase()` would in principle find the victim's organization when its upper-case id is sent by its own owner — but here the sender is the *other* owner, so the lowercased id is not in the attacker's `owned` list and the attacker is also not a member. Confirmed 404 is reached by the same path.
- **`POST /sites` smuggle is correct for the attacker.** `siteInputSchema` is strict; the attacker-victim pair uses `organizationId: victim.organizationId`, which fails `chooseOrganization` with `NotOrganizationOwnerError` → 403 "Only the owner of an organisation can add a site to it". A random UUID gives the exact same error and status. Confirmed with `src/provisioning/http-errors.ts`.
- **The `disposable()` change is necessary.** Without `organizationId`, after `smuggleWrites` has created a second organization for the attacker via `POST /organizations`, `chooseOrganization` throws `OrganizationRequiredError` → 400, and the sweep would start failing on the `DELETE /sites/:id` disposable step. Supplying the original organization keeps the attacker-site creation deterministic. Verified against `provisioning.service.ts:231–244`.
- **No account enumeration or cross-tenant leak oracle.** `leakIn()` checks for the victim's tag (`acorn`/`birch`/`pinecone`) in response text and for any id from the victim's `ownedIds` not supplied by the request. The chosen tag `pinecone` for the sibling site is nowhere in Acorn's own data, so false positives there are not possible.
- **ROUTES floor bumped from 32 → 34.** The actual route table now contains 34 entries (counted from `ROUTES` plus the two new ones). The "greater than 25" floor stays safe. `UC-TI-01` would also fail by name if either new route were missed in `ROUTES`.
- **Invitation lookup assertion updated to match the shipped `InvitationLookup` type** in `src/invitations/invitations.service.ts:34–44` (now includes `site.id` and `organization: { id, name }`); `JSON.stringify(found.body).not.toMatch(/birch/i)` still rules out the other tenant.
- **Timeouts, DB reads, imports, and lint invariants.** Test timeouts set to 120 s (consistent with the sibling file; scrypt at production cost is slow). No `DataSource`/`EntityManager`/`Repository` imports leak outside the test file (allowed in `test/**` by `.oxlintrc.json`). ESM `.js` relative imports used. No new npm packages. No entity or migration changes.
- **CLAUDE.md addition** is accurate to the code: `POST /organizations` writes to `organizations.owner_id` (verified in `provisioning.repository.ts`); `GET /organizations/:id/team` is in `ROUTES`; the `disposable()` reason is explained correctly.
